## Довідка з реалізації для розділів 1 та 2 КР
Тема: Інтелектуальна система рекомендацій мультимедійного контенту.
Документ містить фактичну реалізацію системи у форматі, придатному для звірки з тестом КР та внесення правок у Word.

# Розділ 1 — для вставки

## 1.1 Опис предметної сфери

Мультимедійний контент сьогодні розподілений між трьома основними доменами: музика, фільми, відеоігри. Кожен домен обслуговується власною екосистемою сервісів рекомендацій (Spotify, Netflix, Steam), що формують ізольовані смакові профілі користувача. Користувач, який має чіткі вподобання у фільмах, не отримує користі з цього сигналу під час пошуку музики чи ігор, і навпаки.

Завдання рекомендаційної системи у цій предметній сфері — отримати на вхід множину вподобань користувача та повернути впорядковану множину невідомих йому елементів каталогу, найбільш близьких до його смаку. У межах одного домену задача добре вивчена (content-based filtering, collaborative filtering, hybrid). Cross-domain — слабко покрита: домени мають принципово різну лексику опису (плот, геймплей, музичні теги), тому пряме застосування семантичних методів дає низьку якість.

Реалізована система працює з трьома доменами одночасно: треки (Last.fm), фільми (TMDB), ігри (RAWG). Каталог: ~100 треків, ~100 фільмів, ~113 ігор. Користувач формує профіль вподобань через лайки. Система видає три види рекомендацій: однодоменні, крос-доменні, та смакове порівняння між користувачами.

## 1.2 Огляд та аналіз наявних аналогів і публікацій

**Однодоменні комерційні системи:**
- Spotify, Apple Music, Last.fm — рекомендація музики на основі collaborative filtering та частково content-based підходів.
- Netflix, IMDb, Letterboxd — рекомендація фільмів за поведінковими сигналами.
- Steam, RAWG, IGDB — рекомендація ігор за тегами, жанрами, історією покупок.

Спільна риса: кожна система працює виключно у своєму домені. Сигнал з інших доменів не використовується.

**Cross-domain підходи у літературі:**
- Класичні роботи з cross-domain рекомендацій (Cantador et al.) спираються на overlapping users — спільні користувачі для двох доменів забезпечують transfer сигналу.
- Сучасні підходи на основі вкладень (Khan, Said, Torkamaan — оглядові статті 2020-2023) пропонують відображати елементи різних доменів у спільний латентний простір.
- Слабкість загальних embedding-моделей у cross-domain: різна лексика (плот фільму vs механіки гри vs опис альбому) дає низьку cosine-схожість навіть для тематично близьких елементів.

**Близькі академічні проєкти:** Cross-Domain Recommender Systems (CDRS) як підгалузь Recommender Systems; роботи на основі large language models для семантичної нормалізації (LLM as embedding generator) — Wang et al. 2024 та наступні.

**Висновок огляду:** комерційних систем, що рекомендують контент через границі доменів (фільм → гра, музика → фільм), у відкритому доступі практично немає. Існуючі академічні підходи не використовують LLM як проміжний нормалізатор для побудови спільного смакового простору.

## 1.3 Постановка задачі

**Актуальність.** Користувач сучасних медіа-сервісів формує смак у трьох незалежних доменах, але отримує ізольовані рекомендації. Єдина точка входу до мультимедійних рекомендацій, що зв'язує всі три домени за смисловою близькістю, відсутня.

**Мета.** Розробити інтелектуальну систему рекомендацій мультимедійного контенту, що поєднує однодоменні алгоритми (на основі тегів) та крос-доменні (на основі семантичної близькості через LLM-нормалізовані вкладення), з підтримкою соціального порівняння смаків.

**Об'єкт дослідження.** Процеси формування персоналізованих рекомендацій мультимедійного контенту у середовищі з кількома доменами (треки, фільми, ігри).

**Предмет дослідження.** Методи та алгоритми побудови content-based та cross-domain рекомендацій, а також архітектурні рішення для семантичної нормалізації різнодоменних описів через генеративні мовні моделі.

**Завдання для досягнення мети:**
1. Зібрати уніфікований каталог трьох доменів через відкриті API (TMDB, RAWG, Last.fm).
2. Реалізувати content-based рекомендаційний алгоритм у межах одного домену на основі TF-IDF та косинусної подібності.
3. Реалізувати крос-доменний алгоритм на основі генеративних вкладень, де LLM (Anthropic Claude) виконує роль семантичного нормалізатора, що переводить описи з різних доменів у спільний experiential простір.
4. Побудувати hybrid scoring з re-rank на основі semantic + tag overlap.
5. Розробити веб-інтерфейс з реєстрацією, лайками, рекомендаціями (однодоменними та крос-доменними), пошуком, профілями користувачів, соціальними функціями.
6. Провести експериментальну оцінку якості однодоменних та крос-доменних рекомендацій з порівнянням до базових алгоритмів.

# Розділ 2 — для вставки

## 2.1 Методи для вирішення поставленої задачі

### 2.1.1 Однодоменна рекомендація: TF-IDF + cosine similarity

Метод content-based filtering. Кожен елемент каталогу представлений множиною тегів (genres, tags, keywords). Користувач представлений сумою тегових векторів його лайків, зважених через IDF.

**Term Frequency:** для item-vectors використано бінарне представлення — тег присутній або відсутній (на коротких списках тегів довжина (TF) майже не несе сигналу).

**Inverse Document Frequency:**

    IDF(t) = log(N / (df(t) + 1))

де N — загальна кількість елементів у домені, df(t) — кількість елементів, що містять тег t. Знаменник +1 уникає ділення на нуль та згладжує дуже частотні теги.

**User vector:** для кожного тега t, що зустрічається у списку лайків користувача,

    u[t] = sum over liked items containing t of IDF(t)

**Item vector** (бінарний):

    v_i[t] = 1, якщо item i містить тег t, інакше 0

**Косинусна подібність:**

    cos(u, v_i) = (u · v_i) / (||u|| × ||v_i||)

Алгоритм повертає top-K елементів за спаданням cos(u, v_i), виключивши вже улюблені.

**Параметр min_df:** для домену фільмів використано min_df = 2 (тег має зустрічатись щонайменше у 2 елементах, щоб увійти до словника). Це фільтрує шумні keyword-теги, унікальні для одного фільму. Для треків і ігор min_df = 1.

### 2.1.2 Крос-доменна рекомендація: vibe-pipeline на основі LLM-нормалізації

Загальні embedding-моделі (sentence-transformers, BERT) погано працюють на сирих описах різних доменів, бо лексика розрізняється: фільм описується через плот, гра — через механіки, трек — через виконавця і album notes. Прямий cosine у такому просторі низький (0.5–0.7) навіть для тематично близьких пар.

**Запропоноване рішення.** LLM (Claude Haiku 4.5) виконує роль семантичного нормалізатора. Для кожного елемента у трьох доменах генерується vibe_text — параграф 60-90 слів у спільному experiential словнику (mood, energy, atmosphere, activity-fit, thematic abstractions), без згадок назви, плоту, механіки чи інструментів. Цей параграф потім вкладається у 384-вимірний вектор через sentence-transformers/all-MiniLM-L6-v2 та зберігається у колонці embedding (тип vector(384), розширення pgvector PostgreSQL).

**Семантична близькість** обчислюється як cosine у вкладеному просторі:

    sem(a, b) = 1 - cosine_distance(emb(a), emb(b))

де cosine_distance у pgvector нотації <=>.

**Hybrid scoring.** До чистого semantic-сигналу додається бонус за перетин тегів — для випадків franchise-матчингу (Spider-Man movie ↔ Spider-Man game), де семантика недостатня:

    bonus(a, b) = min(MAX_BONUS, |tags(a) ∩ tags(b)| × TAG_BONUS)
    hybrid(a, b) = min(1, sem(a, b) + bonus(a, b))

Константи: TAG_BONUS = 0.07 за один спільний тег, MAX_BONUS = 0.35 (щоб семантика залишалась домінуючим сигналом).

**Pool re-rank.** Для кожного anchor спочатку через pgvector отримується pool з K × 4 кандидатів за чистим semantic. Потім pool пере-ранжується у Python за hybrid scoring, і повертається top-K.

**Display calibration.** LLM-нормалізовані вкладення концентрують схожі елементи у вузькому діапазоні (0.55-0.95 raw cosine), випадкові пари — 0.58-0.62. Тому raw 60% виглядає як "збіг 60%", хоча це по суті шумовий поріг. Для відображення застосовано лінійне перетворення:

    displayed = clamp((hybrid - 0.5) × 2, 0, 1) × 100

де raw 0.50 → 0%, 0.75 → 50%, 0.90 → 80%, 1.00 → 100%.

### 2.1.3 Соціальне порівняння смаків з LLM-інсайтом

При перегляді профілю іншого користувача система обчислює:
- **Перетин лайків** — спільно вподобані елементи з трьох доменів.
- **Сумісність смаків** — cosine між векторами топ-тегів двох користувачів (зважено через IDF, як у п. 2.1.1).
- **Distinctive picks** — елементи з бібліотеки другого користувача, що несуть теги, відсутні у бібліотеці першого; ранжуються за різницею вагових векторів (their_vec − my_vec).
- **LLM-інсайт** — Claude Haiku генерує 3 речення (~80-100 слів): що спільне, що відрізняється, що варто спробувати з distinctive picks.

### 2.1.4 AI-пояснення крос-доменних рекомендацій

Для кожної пари (anchor, recommendation) система може згенерувати одне речення у плейн англ., що пояснює спільність на рівні mood/energy/theme. Виклик LLM відбувається лише за ініціативою користувача (по кліку на кнопку "Why?"). Результат кешується у таблиці cross_explanations з композитним ключем (anchor_type, anchor_id, rec_type, rec_id). Повторний виклик тієї самої пари не витрачає токенів LLM.

### 2.1.5 Гібридний пошук

Реалізовано три режими пошуку:
1. **Substring** — підрядковий пошук по title, artist, director, tags, genres. Швидко, нульова вартість, точно знаходить точні збіги.
2. **Semantic supplement** — для тих доменів, де substring знайшов менше 3 збігів, додається до 3 семантичних результатів через pgvector + on-the-fly embedding запиту через all-MiniLM-L6-v2. Спрацьовує для vibe-запитів типу "melancholy night drive".
3. **AI mode** — повний запит до LLM, який обирає до 5 елементів з кожного домену з поясненням однією фразою. Викликається лише за явним вибором користувача.

## 2.2 Технології розробки системи

### 2.2.1 Backend
- **Python 3.10+**
- **FastAPI** — web-framework для побудови REST API.
- **psycopg2** — драйвер PostgreSQL.
- **scikit-learn** — обчислення cosine similarity (sklearn.metrics.pairwise.cosine_similarity).
- **NumPy** — векторні обчислення.
- **anthropic** — офіційний SDK для Claude API.
- **sentence-transformers** — модель all-MiniLM-L6-v2 для побудови embedding-векторів (384 виміри, ~22M параметрів).
- **python-dotenv** — конфігурація через .env.

### 2.2.2 База даних
- **PostgreSQL** (хостинг Neon).
- **pgvector** — розширення для зберігання вкладень як тип vector(384) та операцій cosine_distance / L2 / inner product.
- Таблиці: users, tracks, movies, games, likes, friend_requests, friendships, cross_explanations.
- Колонки embedding (vector) та vibe_text (TEXT) додаються до tracks, movies, games.

### 2.2.3 Frontend
- **Astro 6** — meta-framework для статичних сторінок з островами інтерактивності.
- **React 19** + **TypeScript** — інтерактивні компоненти (rekомендаційні списки, граф вкусу, картки, форми).
- **Tailwind CSS v4** — utility-first стилізація.
- **Firebase Auth** — Google OAuth.

### 2.2.4 Зовнішні джерела даних
- **TMDB API** — метадані фільмів (genres, keywords, overview, cast, ratings).
- **RAWG API** — метадані ігор (genres, tags, description, platforms, ratings).
- **Last.fm API** — метадані треків (artist, album, tags, listeners, summary).

### 2.2.5 LLM
- **Claude Haiku 4.5** (модель claude-haiku-4-5-20251001):
  - Генерація vibe_text для всіх 313 елементів каталогу (одноразово).
  - Генерація AI-пояснень крос-доменних пар (по запиту, з кешуванням).
  - LLM-інсайт для порівняння смаків користувачів.
  - AI-режим пошуку.

### 2.2.6 Інструменти оцінки
- **matplotlib** — побудова стовпчастих діаграм та графіків ranking discrimination.
- Власні скрипти evaluation/single_domain/evaluate.py та evaluation/cross_domain/evaluate.py з multi-seed підходом (5 random seeds → mean ± std).

# Підказки для адаптації під написане

1. **Якщо у Word описано collaborative filtering** — у реалізації його немає. Можна замінити на "content-based filtering з TF-IDF зваженням" або додати у Розділ 1 згадку, що CF свідомо не використовується через cold-start проблему та малий розмір каталогу.

2. **Якщо у Word фігурує deep learning** — у реалізації використано лише pre-trained sentence-transformers (all-MiniLM-L6-v2), власних мереж не навчалось. Можна формулювати як "transfer learning на основі pre-trained transformer-моделі".

3. **Якщо у Word згадано matrix factorization** — у реалізації його немає. Видалити або замінити на "TF-IDF з cosine similarity".

4. **Якщо описано Word2Vec, GloVe, doc2vec** — використано саме sentence-transformer (sentence-BERT family), 384-dim. Уточнити модель.

5. **Якщо описано що embedding генеруються з сирого тексту** — це не так. Embedding генеруються з vibe_text, який своєю чергою генерується LLM з метаданих. Це ключове архітектурне рішення, варто описати окремо.

6. **Якщо описано що algorithm повертає просто cosine** — у крос-доменному режимі використовується hybrid (semantic + tag bonus) та pool re-rank.

7. **Якщо описано що рекомендації формуються "у режимі real-time"** — насправді каталог завантажується в кеш на запуску бекенду, а user-specific рекомендації обчислюються при першому запиті та кешуються у пам'яті.
